# 技术结构说明

## 文档定位

这份文档说明当前仓库的技术拆分方式、主流程和后续扩展策略，目标是帮助继续维护这个项目的人快速理解“代码为什么这样组织”。

项目采用的整体思路是：

- 用 TypeScript 维护核心逻辑和配置
- 用微信小游戏要求的最小入口加载编译产物
- 用 Canvas 2D 自绘机台、物体和界面
- 通过模块拆分，把玩法、渲染、平台适配和服务预留解耦

## 运行入口

运行链路很简单：

1. 微信小游戏加载根目录 `game.js`
2. `game.js` 引入 `dist/index.js`
3. `src/index.ts` 创建 `Game` 实例并启动主循环
4. `Game` 负责装配状态、输入、渲染、物理、奖励和 UI

这种入口结构兼顾了两个目标：

- 满足微信小游戏工程的目录要求
- 保持业务逻辑集中在 `src/` 中维护

## 模块划分

### `src/core`

核心调度层，负责把游戏跑起来。

- `Game.ts`：总装配入口，串起状态、输入、更新、渲染和结算
- `GameLoop.ts`：帧循环调度
- `GameState.ts`：运行时状态快照与 HUD 数据来源
- `EventBus.ts`：轻量事件分发
- `render/CanvasSceneRenderer.ts`：机台和场景的总渲染编排
- `render/Pseudo3DProjector.ts`：伪 3D 投影与排序辅助

### `src/gameplay`

玩法对象和生成逻辑所在层。

- `CoinSpawner.ts`：硬币生成
- `RewardSpawner.ts`：奖励块初始生成与补位
- `ComboTracker.ts`：连击窗口与额外奖励
- `entities/`：硬币、推板、奖励块以及它们共享的基类
- `renderers/`：具体对象的绘制器
- `rewards/RewardSystem.ts`：掉落奖励扩展点，目前仍是占位接口

### `src/physics`

负责场内对象更新和掉落判定。

- `PhysicsWorld.ts`：推进、边界限制、物体分离、掉落收集
- `LandingResolver.ts`：支撑高度、堆叠层级和落位辅助

这层当前已经不是“纯占位”，而是原型玩法成立的关键实现。

### `src/ui`

负责可交互与可读反馈。

- `Button.ts`：投币按钮
- `Hud.ts`：左上角信息面板和提示文字
- `DropFeedbackOverlay.ts`：掉落闪光、浮字和 Combo 文案

### `src/data`

- `gameConfig.ts`：集中管理尺寸、颜色、布局、物理参数、奖励权重和 UI 配置

这是项目非常重要的一层。当前很多玩法调整都可以先从这里下手，而不是到处改魔法数字。

### `src/platform`

- `miniGameAdapter.ts`：微信小游戏平台适配，封装 `wx` 能力、Canvas、帧调度和触摸输入

### `src/services`

平台能力预留层。

- `SaveService.ts`：存档接口预留
- `AudioService.ts`：音效接口预留
- `CloudService.ts`：云同步接口预留

这些文件已经接入调用点，但内部实现仍然是空壳，适合后续逐步替换。

### `src/utils` 与 `src/types`

- `utils/`：数学和通用辅助方法
- `types/`：微信小游戏环境类型声明

## 当前主流程

### 1. 启动阶段

- 创建平台适配器，读取屏幕尺寸
- 基于屏幕尺寸生成运行时配置
- 初始化状态、推板、物理世界、生成器、HUD 和按钮
- 注册输入和事件
- 初始化首批奖励块

### 2. 输入阶段

- 玩家点击投币按钮
- `CoinSpawner` 生成一枚新的硬币对象
- 状态记录总投币数
- 触发音效调用点

### 3. 更新阶段

每帧主要执行以下逻辑：

- 更新推板
- 更新连击计时器和掉落反馈
- 调用 `PhysicsWorld` 更新场内对象
- 收集越过前沿掉落线的物体
- 结算奖励与连击
- 在奖励块不足时自动补位
- 同步 HUD 展示用状态

### 4. 渲染阶段

- 清空画布
- 绘制背景、机台、轨道和前景结构
- 按伪 3D 排序绘制硬币与奖励块
- 绘制反馈层
- 绘制 HUD 和投币按钮

## 为什么这样拆

### 1. 装配层和业务层分开

`Game.ts` 负责把模块连起来，而不是把所有玩法细节都塞进去。这样继续增加奖励逻辑、调试能力或平台接入时，不会让入口文件迅速失控。

### 2. 对象状态和表现层分开

硬币、奖励块和推板的数据结构在 `entities/` 中，具体怎么画在 `renderers/` 中。这样后续替换视觉表现时，不需要重写玩法逻辑。

### 3. 参数集中管理

布局、物理、奖励权重和 UI 样式都集中在 `gameConfig.ts`，非常适合原型期反复调手感。

### 4. 平台能力先留接口，再逐步接真实现

项目已经在流程上预留了存档、音效和云同步的接入点，因此后续不需要为这些能力重构整体结构。

## 当前技术判断

从代码状态来看，这个项目已经完成了“工程能跑”这一层，下一步的主要技术问题不再是补目录，而是：

- 如何继续提高前沿碰撞和堆叠的稳定性
- 如何给调参提供更直接的观测手段
- 如何在不破坏现有结构的前提下接入平台能力
- 如何把奖励与长期循环继续扩展，而不让 `Game.ts` 变成新的大杂烩

## 后续技术建议

- 为关键物理参数增加调试输出或可视化辅助
- 让奖励、存档和音效的实现继续保持模块独立
- 控制 `Game.ts` 的职责边界，把新增逻辑优先放回对应模块
- 优先通过 `gameConfig.ts` 调优，而不是把数值散落进实现细节
